## Context

当前 `develop` 只保留 OpenSpec 骨架，完整产品基线位于 `4627911`。v2.2.3 是宿主驱动的 Skill：根 `SKILL.md` 定义工作流，`boundary-guard.py` 负责边界分类，`match-experts.py` 负责专家匹配，宿主模型负责语义判断、用户交互、人格演绎和综合。原版问题集中在目录混杂、两份 Registry、两套匹配实现，以及根 Skill、Brain Crew、references、README、Changelog 和测试报告之间的冲突。

本设计只做三类工作：恢复产品、优化目录、收敛重复和冲突。冲突处理采用已经确认的最小改动原则，不得以“更稳定”或“更易测试”为由把 Skill/大模型职责迁移给程序。

## Goals / Non-Goals

**Goals:**

- 恢复 v2.2.3 的完整产品链路和 40 位专家资产。
- 保持根 Skill、宿主模型和原有脚本的职责边界。
- 只保留一个 Registry，删除旧副本和空备份。
- 只收敛原本已经程序化的专家匹配重复实现。
- 将全部已确认冲突写成一张可验证的裁决表。
- 只按文件完整性核查专家 Skill，并从固定源原样恢复缺失资产。
- 修复测试退出码、现场恢复、路径解析和历史证据混放等工程缺陷。

**Non-Goals:**

- 不新增路由控制器、名单确认状态机、人格预检状态机、会议控制器或结果校验运行时。
- 不把路由、点名/排除/替换、名单确认、人格加载、会议综合或七类输出迁移到 Python。
- 不新增会议模式、Boundary 领域、专家选择维度或用户交互节点。
- 不兼容已删除的旧 Registry 文件或路径。
- 不评价、改写或扩写专家人格，不由模型补齐专家文件。
- 不实现真实多 Agent 隔离、会话持久化、在线服务、数据库或外部实时数据。

## Decisions

### 1. 冲突按固定优先级和最小改动处理

冲突来源采用以下优先级：

1. 根 Skill 的正式工作流。
2. 产品主链路可执行脚本的实际行为。
3. Brain Crew Skill 与 Query API；其接口保留，但业务逻辑向主链路收敛。
4. references、README、Changelog 和历史报告；它们只能被修正，不能反向定义产品行为。

这个顺序只用于解决现有冲突，不授权新增产品逻辑。实施与验收以本文裁决表为差异白名单，表外差异一律视为回归。

### 2. 根 Skill 保留完整可执行协议

目标结构如下：

```text
ask-five-pro/
|-- SKILL.md                         # 完整规范性工作流
|-- README.md                        # 安装、触发、能力与边界
|-- references/
|   |-- mode-templates.md            # 六模式展开模板
|   |-- output-examples.md           # 非规范性示例
|   |-- anti-patterns.md             # 反例和自检说明
|   `-- expert-fallback-profiles.md  # 原有 fallback 资产
|-- brain-crew/
|   |-- SKILL.md
|   |-- expert-registry.json         # 唯一 Registry
|   |-- flash-profiles.md
|   `-- packs/<pack>/<expert>/...
|-- scripts/
|   |-- boundary-guard.py
|   `-- match-experts.py             # 根 Skill 原调用入口
|-- brain-crew/scripts/
|   |-- matching_core.py             # 原有脚本逻辑的共享实现
|   |-- brain_crew_query.py          # 原函数入口的薄适配层
|   `-- validate-expert-assets.py    # 离线完整性检查
`-- tests/
    |-- fixtures/
    |-- regression/
    |-- compatibility/
    |-- assets/
    `-- evidence/                    # 历史证据，不参与当前判定
```

根 `SKILL.md` 可以移出重复安装说明、Changelog 和长示例，但必须保留阶段顺序、所有分支、脚本调用、用户确认、暂停/终止和输出要求。references 不得成为只有读取后才能发现关键运行规则的隐性入口。

### 3. 唯一 Registry 位于 Brain Crew

`brain-crew/expert-registry.json` 是唯一事实源。`references/expert-registry.json` 和空 `.bak` 直接删除，不建立符号链接、包装文件或路径重定向；旧路径调用方必须迁移，因此这是明确的 breaking change。

Registry 元数据采用三层标识：

| 字段 | 含义 | 用途 |
|---|---|---|
| Registry/frontmatter `id` | 稳定机器 ID | 跨文件关联、匹配与校验 |
| frontmatter `name` | Skill/目录名 | 资产路径与 Skill 身份 |
| Registry `name` | 显示名 | 用户可见名单和输出 |

原来缺少 `default_enabled` 的 5 条记录显式补 `false`；所有 `bundled` 字段删除。除已批准字段和可移植路径表达外，不改写专家业务元数据，也不修改专家源文件内容。

### 4. 只收敛原本已经程序化的匹配

根 Skill 继续调用 `scripts/match-experts.py`。共享 `matching_core.py` 以该脚本的评分、模式加权、重新排序、目标人数和非正分停止逻辑为基线。`brain_crew_query.py` 保留原函数入口，只做参数、路径、批量查询和返回格式适配，不再维护评分副本。

共享实现只接受两类已批准结果修正：

- 双向类别别名：团队↔组织、技术↔工程、风险↔风控。
- 敏感专家默认排除，仅在用户明确点名或对抗模式时进入候选。

点名、排除、替换和名单确认仍由根 Skill 与宿主模型处理；匹配模块不持有确认状态。`turbo` 只属于 Query API 批量查询，不进入会议模式枚举。

### 5. Boundary Guard 以脚本实际行为为准

`boundary-guard.py` 保持固定领域/置信度扫描顺序、首个命中、单领域输出和三种 action。文档中“合并多个领域”或“取最严格结果”的表述被修正，不修改脚本去迎合这些表述。除必要的路径与测试可用性修复外，不重写其业务逻辑。

### 6. 完整冲突裁决表

| # | 冲突点 | 最终裁决 | 改动性质 |
|---:|---|---|---|
| 1 | 两份 Registry | 只保留 `brain-crew/expert-registry.json` | 重复收敛 |
| 2 | 旧 Registry 是否兼容 | 删除旧文件、`.bak` 和旧路径支持 | BREAKING 目录清理 |
| 3 | `id`、frontmatter `name`、Registry `name` 混用 | 分别定义为机器 ID、Skill/目录名、显示名 | 冲突澄清 |
| 4 | 5 条记录缺 `default_enabled` | 显式补 `false` | 数据规范化 |
| 5 | Registry `bundled` 冗余 | 删除字段，不改专家文件 | 冗余收敛 |
| 6 | 根 Skill 匹配入口 | 继续调用 `scripts/match-experts.py` | 保持原职责 |
| 7 | Query API 自有评分 | 保留函数入口，删除重复评分，改为薄适配 | 重复收敛 |

| 24 | 根 Skill 默认启用状态 | 保持 `default-enabled: false`，修正文档冲突 | 文档向入口对齐 |

### 7. 专家组只做源文件完整性核查

为 40 位专家记录源仓库、固定 commit/tag 和源路径，然后只核对主 `SKILL.md`、被本地引用且随源 Skill 发布的附属文件、Registry 路径、三层标识关系和 Flash 映射。缺失、损坏或未经批准的差异从固定源原样恢复。

不建立人格质量 rubric，不评价专家观点，不扩写内容。固定源无法取得时报告阻塞，不生成替代文件。

### 8. 测试可靠性缺陷直接修复

以下属于测试与材料可靠性，不改变产品逻辑：

| 缺陷 | 处理 |
|---|---|
| 当前检查失败仍返回成功 | 任一必需检查失败即返回非零 |
| Registry 替换测试污染工作区 | 使用必定执行的恢复逻辑覆盖成功、失败和异常路径 |
| 校验脚本依赖 cwd | 按脚本/安装位置或显式参数解析路径 |
| 文档出现 34/39/40 人 | 当前材料统一为 40 人 |
| README pack 数不一致 | 当前材料统一为 5 个 pack |
| 历史报告与当前结果混放 | 移入 `tests/evidence/` 并明确非当前证据 |
| 旧 Engine-only 说明、空 `.bak` | 从生产材料删除 |

测试只用于证明兼容，不参与会议运行，也不通过新增运行时对象模拟产品控制链。

## Risks / Trade-offs

- [删除旧 Registry 路径会破坏旧调用方] → 在 proposal、README、迁移说明和测试中明确 breaking change，并要求调用方改用唯一路径。
- [文档拆分导致模型漏读规则] → 根 Skill 保留完整规范性链路，references 只放展开材料，并用规则清单逐项复核。
- [共享匹配改变边缘排序] → 先固化原主脚本 fixture，再做跨入口差异测试；只接受裁决表第 9、11 项差异。
- [三组类别别名扩大匹配范围] → 只实现列明的双向映射，并用负例证明未自动增加其他别名。
- [源仓库不可获得] → 保持专家完整性检查失败，不用生成内容绕过。
- [本地门禁被误称真实宿主验证] → 最终报告分开列示静态、脚本、资产、本地宿主和真实宿主状态。

## Migration Plan

1. 从 `4627911` 固化全量文件、职责、两份 Registry、40 人资产、八个 Prompt 和脚本 fixture。
2. 原样恢复基线文件并建立逐文件迁移表，再整理根 Skill、references 和历史材料。
3. 建立唯一 Registry，删除旧文件与 `.bak`，应用三层标识、默认值和字段清理。
4. 以原 `match-experts.py` 提取共享匹配，实现三组别名和敏感过滤；将 Query API 改为薄适配。
5. 只修正 Boundary 与工作流文档冲突，不迁移 Skill/模型职责。
6. 从固定源核查并原样恢复 40 位专家资产。
7. 修复测试退出码、现场恢复和 cwd 独立性，分离当前结果与历史证据。
8. 运行完整门禁并生成差异报告；表外差异必须回退或另行取得用户批准。

实施提交按“基线恢复、目录整理、Registry 收敛、匹配收敛、专家恢复、测试收尾”分层，任一层出现表外行为变化可独立回退；`4627911` 始终只读。
